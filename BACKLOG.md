## Запросы / SQL-нюансы

- **`ORDER BY task_history.created_at` всегда с тай-брейкером по `id`.**
  Несколько событий могут попасть в одну миллисекунду (`accepted` и follow-up `commented` от одного клика), поэтому сортировка по `created_at` без вторичного ключа нестабильна. Везде, где история сортируется по времени, использовать `ORDER BY created_at ASC, id ASC`.
  ✅ Закрыто на Этапе 7: `HistoryRepository.list_by_task` уже с тай-брейкером, новые архивные запросы используют COALESCE+id DESC.

## БЛОК 3 — заметки с Этапа 3

  `RoleFilter` возвращает `False` при отказе (с уведомлением «Недостаточно прав»), но aiogram продолжает искать следующий совпадающий хэндлер. На пиковых нагрузках — рассмотреть split на «INSERT + flush → commit, потом постинг → UPDATE message_ids в новой транзакции» с компенсацией при провале постинга. Для MVP допустимо.

## БЛОК 6 — заметки с Этапа 6

- **[ETAP-7+] check_overdue: gather-параллелизм для DM leads/admin.**
  Сейчас `notify_overdue` шлёт DM последовательно через `send_dm_safe`. На задачах с большим числом recipients (десятки админов/leads) это даст ощутимую задержку. На Этапе 7+ обернуть в `asyncio.gather(*[send_dm_safe(...) for ...])` с return_exceptions=True. Дополнительно — продумать, не выйдем ли за rate-limit Telegram (30 сообщений/сек на бота); при необходимости — `asyncio.Semaphore(20)` + small delay.

- **[ETAP-7+] purge_completed: транзакция держится во время bot.delete_message.**
  `purge_completed_messages` сначала собирает список, потом удаляет с TG, потом одной транзакцией ставит флаги. Между `bot.delete_message` и UPDATE задача может уже завершиться/восстановиться (маловероятно). Допустимо для MVP. На Этапе 7+ — split: TG-вызовы вне транзакции, потом отдельной транзакцией UPDATE по списку успешных id. ✅ Закрыто на правке после Этапа 6: две отдельные сессии, TG-вызовы между ними без открытой транзакции БД, финальный bulk UPDATE одной транзакцией.

- **[ETAP-7+] Recovery после долгого даунтайма бота.**
  Если бот лежал >2 часа, h2-reminder для задач с deadline через 2 часа уже в прошлом — bootstrap пропустит их (timepoint `<= now()`). Соответствующее уведомление просто не уйдёт. Альтернатива: при bootstrap'е, если timepoint в прошлом и `reminder_*_sent=False` — выслать сразу (компенсаторно). Сейчас пропускаем — приоритет «не спамить старыми напоминаниями».

- **[ETAP-7+] APScheduler MemoryJobStore — job'ы теряются при рестарте.**
  Per-task DateTrigger переcоздаются bootstrap'ом из БД, поэтому effectively persistent (через `reminder_*_sent` флаги). Но если хочется без bootstrap'а — переехать на SQLAlchemyJobStore. Сейчас MemoryJobStore + bootstrap проще и точнее (источник правды — БД).

- **[ETAP-7+] Service-level integration тесты для scheduler-job'ов.**
  Та же проблема, что в БЛОКЕ 5: jobs открывают свою сессию через `async_session_factory`, изоляция от тестового conftest. Покрыто чистыми helper-тестами (21 шт.) + ручным smoke. Полные интеграционные тесты — рефактор conftest или session-injection в job'ах.

- **[ETAP-7+] Визуальный overdue-индикатор в карточке отдела.**
  Сейчас overdue только в DM, в топике карточка остаётся с эмодзи «🟡 В работе» / «🆕 Новая». Можно добавить третий вариант «🔴 Просрочена» в `render_task_card` при `task.status in (new, in_progress) AND deadline < now()`. Реализовать одновременно с детальной карточкой задачи на Этапе 7 (архив) — там будет общая страница «история задачи», есть смысл сразу довести визуальные состояния.

- **[ETAP-7+] `check_overdue` и `bootstrap_scheduler` делают SELECT без явного `async with session.begin()`.**
  Работает (read-committed), но рассогласовано с инвариантом проекта «сессии всегда в begin()». Привести к единообразию вместе с другими стилистическими правками.

- **[ETAP-7+] Файлы задачи: message_ids не сохраняются → не покрываются `purge_completed`.**
