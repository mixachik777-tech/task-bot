# DECISIONS.md

Решения, которые принял Claude сам, не описанные явно в PROJECT_PLAN.md.
Перечитывается перед началом каждого нового этапа.

## Процедурные правила (применяются всегда)

- **Промежуточные отчёты — только bash cat, никогда Read tool.** Read сворачивает вывод многих файлов в один collapsed blob («Read N files (ctrl+o to expand)») — пользователь не видит содержимое и не может ревьюить. cat вываливает stdout целиком в чат, как и положено в отчёте. Зафиксировано после провала отчёта по Этапу 4.
- **Любая правка `app/db/models.py` или новая Alembic-миграция → СТОП и согласование с пользователем перед написанием.** Это «п.2 — когда остановиться вне отчёта» из автономного промпта. На Этапе 4 я молча добавил `AppSetting` + миграцию `b6f4a1e25c08` — пользователь это решение принял по факту, но в будущем требует явного согласования. Решение в .env vs БД — обсуждать и брать `ОК` до начала кодинга.

## Этап 4

- **Хранение TASK_CHAT_ID и LEADERSHIP_TOPIC_ID — в БД, новая таблица `app_settings(key, value)`.** Почему: команды `/set_chat` и `/set_leadership_topic` должны вступать в силу мгновенно, без рестарта контейнера; .env требует ручного редактирования + рестарта; одна k/v-таблица проще, чем отдельные колонки в `departments` (которая для отделов, а не для общих настроек), и переиспользуется на будущее (например, под флаги фич).

- **TASK_CHAT_ID + LEADERSHIP_TOPIC_ID читаются из `app_settings` каждый раз при создании задачи, не кешируются в памяти процесса.** Почему: после `/set_chat` старые задачи должны постится в новый чат без рестарта; запрос — один SELECT в строку, дешёвый.

- **Формат `callback_data` для FSM создания задачи — `ct_<step>:<value>`** (`ct_dept:<id>`, `ct_pri:<priority>`, `ct_desc_skip`, `ct_files_done`, `ct_send`, `ct_edit`, `ct_cancel`). Почему: понятный префикс `ct_` (create_task) отделяет от карточек задач (`task_*`); строковый split по `:` без CallbackData-фабрики — Этап 4 простой, на 5+ может усложниться → вынесу в CallbackData при необходимости.

- **Формат `callback_data` для карточек задач — `task_<action>:<task_id>`** (`task_accept:42`, `task_complete:42`, `task_comment:42`). Почему: action — глагол, task_id — число; парсится `split(":", 1)`. Уже зафиксировано в инвариантах автономного режима как «action:task_id» — добавил префикс `task_` для отделения от ct_-флоу.

- **FSM-states объявлены в `app/bot/states.py`, группа `CreateTask` с 7 состояниями** (department, title, priority, deadline, description, files, preview). Почему: следует структуре проекта; одна группа на FSM — стандартный паттерн aiogram.

- **AuthMiddleware расширен: для не-private чатов делает lookup без create.** Почему: команды `/set_chat`, `/set_topic`, `/set_leadership_topic` выполняются в супергруппе и требуют, чтобы `data["user"]` был доступен для `require_role(ADMIN)`; lookup-only (без create) сохраняет инвариант «не плодить учётки в группах» из BACKLOG БЛОК-3. Закрывает соответствующий пункт BACKLOG.

- **Время в UTC внутри, локальное время на UI.** В БД `deadline` хранится timezone-aware UTC. Утилита `app/bot/utils/time.py::format_dt_local(dt)` использует `settings.TZ` (по умолчанию Europe/Moscow). Все места вывода времени пользователю проходят через неё. dateparser принимает RU-локаль + `PREFER_DATES_FROM=future`.

- **Парсинг даты валидируется: deadline должен быть минимум +5 минут от now().** Почему: страховка от случайных «уже прошедших» дедлайнов из-за неоднозначного парсинга («18:00» сегодня, если уже 19:00 — dateparser с PREFER_DATES_FROM=future перенесёт на завтра, но граничные случаи бывают).

- **Размер файла проверяется как `file_size > 20 МБ` через `MAX_FILE_SIZE = 20 * 1024 * 1024`.** Если размер не указан Telegram'ом — принимаем (редкий кейс stickers / голосовых).

- **На Этапе 4 в карточку задачи добавляются inline-кнопки «✋ Принять в работу» с callback'ом-заглушкой**, отвечающим «Появится на Этапе 5». Почему: визуально карточка готова, Этап 5 заменит заглушку реальным хэндлером без editMessage.

- **Сервис создания задачи `app/services/task_service.py::TaskService.create_task` — одна транзакция БД, внутри которой и постинг в Telegram.** При TelegramRetryAfter — 3 повтора с asyncio.sleep(retry_after). При TelegramBadRequest/TelegramForbiddenError после первого вызова — пробрасываем, транзакция БД откатывается полностью. БД-only режим (когда TASK_CHAT_ID==0 или dept.topic_id==0): задача только в БД, в логах WARNING.

- **`dept_chat_id` сохраняется при постинге в топик отдела**, чтобы Этап 6 знал, где удалять сообщение через 24ч после `done`. На этапе 4 это уже работает.

- **HistoryRepository вынесен в отдельный модуль `app/db/repositories/history.py`**, не часть TasksRepository. Почему: история — независимая сущность, у неё свои методы (log, list_by_task с сортировкой по created_at+id для тай-брейкера из BACKLOG).

### Правки по ревью Этапа 4

- **dept.topic_id фиксируется в локальной переменной `dept_topic_id` до создания task (Правка 1).** В `TaskService.create_task` сразу после получения `dept` сохраняем `dept_topic_id = dept.topic_id` и `dept_code = dept.code`, дальше используем только локальные. Защита от lazy-load surprises на ORM-объекте после flush task в той же сессии.

- **Зеркало в «Руководстве» — без клавиатуры (Правка 2).** В `TaskService.create_task` при отправке в `lead_topic_id` идёт `reply_markup=None`. Только в топике отдела есть кнопки действий. Почему: избегаем перехвата задачи из руководства (lead-кнопка «Принять» → нежданный исполнитель, левый отдел) и упрощаем синхронизацию двух сообщений на Этапе 5 (в архивном — только текст, в основном — текст+клавиатура).

- **Все `cq.message.edit_text` в FSM создания задачи обёрнуты в `_safe_edit_text` (Правка 3).** Хелпер ловит `TelegramBadRequest` и логирует на DEBUG. Сообщение могло устареть (>48ч), быть удалено пользователем, или иметь идентичный текст — во всех случаях UX продолжается через `answer()`.

- **AuthMiddleware: для не-private чатов транзакция обёрнута в `session.begin()` (Правка 4).** Стилистически одинаково с веткой private; явный close транзакции вместо неявного rollback при выходе из контекста.

- **`/set_chat`, `/set_topic`, `/set_leadership_topic` — порядок проверок: chat.type → is_topic_message → args (Правка 5).** Раньше при вызове `/set_topic` без args в личке выводилось «Использование», но не объяснялось, что команду надо вызывать в супергруппе. Теперь сначала проверяется контекст, потом аргументы.

- **`cb_send` в FSM пропускает `asyncio.CancelledError` (Правка 6).** Перед широким `except Exception` стоит `except asyncio.CancelledError: raise`, чтобы остановка таска не маскировалась как «ошибка отправки».

## Этап 5

- **TG-обёртки вынесены в `app/bot/utils/tg.py`** — `send_with_retry`, `edit_text_safe`, `send_dm_safe`. Используются и в `task_service.py`, и в `task_actions.py`. Почему: один источник правды для retry/RetryAfter и обработки «not modified» / «message to edit not found». Локальный `_send_message_with_retry` в task_service.py заменён на этот хелпер.

- **SELECT FOR UPDATE — через `TasksRepository.lock_for_update(session, task_id)`.** Возвращает Task с эксклюзивным локом строки до конца транзакции. Все callback-хэндлеры accept/complete/cancel читают задачу через этот метод. Двойной клик: первый берёт лок, обновляет статус, коммитит; второй ждёт лок, видит уже обновлённый статус → отказ «Задача уже принята @ivanov».

- **Сервис `app/services/task_actions.py::TaskActionsService`** — методы `accept` / `complete` / `cancel` / `add_comment`. Каждый: одна транзакция БД (lock → проверка статуса → ALLOWED_STATUS_TRANSITIONS → UPDATE → INSERT history → sync TG). Уведомления постановщику/исполнителю — ПОСЛЕ commit, best-effort через `send_dm_safe`. Возвращает `ActionResult(success, user_message, task)`.

- **Карточка отдела — с клавиатурой, зеркало в «Руководстве» — без (закреплено Правкой 2 Этапа 4).** При editMessageText: dept-сообщение получает `build_task_card_kb(task.status, task.id)`, arch-сообщение получает `reply_markup=None`. Зеркало синхронизируется только по тексту.

- **`_sync_card` — dept-edit raises на ошибке (rollback DB), arch-edit best-effort.** Если зеркало не отредактировалось (BadRequest, Forbidden), задача всё равно зафиксирована в БД и в основном топике. Рассинхрон зеркала логируется WARNING — не критично, на Этапе 7 (архив) данные берутся из БД, не из зеркального сообщения.

- **Кнопка «❌ Отменить» добавлена в карточку задачи** для статусов NEW и IN_PROGRESS. Permission-check на стороне callback-хэндлера: только `creator_id == user.id` ИЛИ `user.role == admin`. Иначе — alert «Отменить может только постановщик или админ.»

- **Permission-матрица на Этапе 5** (закодирована в callback-хэндлерах, не в сервисе):
  - `task_accept`: любой active-юзер с записью в БД (и не bot).
  - `task_complete`: только assignee задачи или admin.
  - `task_cancel`: только creator или admin.
  - `task_comment`: creator, assignee, admin, lead — комментарий пишется в task_history.
  - Если `data["user"]` отсутствует (юзер не делал /start в личке) → alert «Сначала напишите /start боту в личке.»

- **FSM `TaskComplete.waiting_comment` и `TaskComment.waiting_text`** — текст комментария вводится В ТОМ ЖЕ ЧАТЕ, где была карточка (топик отдела). FSM key — (chat_id, user_id), параллельные пользователи не мешают друг другу. На «Завершить» предлагается inline-кнопка «Без комментария» (callback `tcomp_skip:<task_id>`). Отмена ввода — общий `/cancel`.

- **`task_history.payload`-форматы**:
  - `accepted`: `null`
  - `completed`: `{"result_comment": "..."}` или `null` если skipped
  - `cancelled`: `{"by_role": "creator"|"admin"}` — для будущей аналитики, кто отменил
  - `commented`: `{"text": "...", "from_user_role": "..."}`

- **Уведомления (DM, best-effort)**:
  - accept → creator: «🟡 @x взял задачу #N в работу»
  - complete → creator: «✅ @x завершил задачу #N» + комментарий, если есть
  - cancel → все НЕ-инициаторы (creator+assignee): «❌ @x отменил задачу #N»
  - comment → все НЕ-комментаторы: «💬 @x на задаче #N: <текст>»

- **`task_stubs.py` удалён**, заменён на `task_actions.py`. В `app/main.py` `task_stubs_router` убран, добавлен `task_actions_router`.

## Этап 6

- **APScheduler с per-task DateTrigger для напоминаний (отход от PROJECT_PLAN.md).** PROJECT_PLAN.md предлагал interval-job каждые 5 минут, который сканит ВСЕ задачи и решает, кому слать. Идём другим путём: при создании задачи добавляем 3 DateTrigger-job'а (h2/d1/d2), при complete/cancel — снимаем их. Bootstrap при старте бота сканит все active-задачи и расставляет реминдеры по их `deadline - threshold`, пропуская уже отстреленные (`reminder_*_sent=True`) и timepoint'ы в прошлом. Почему: точнее (с точностью до APScheduler tick), меньше нагрузки на БД, проще понять кто и когда стрельнёт. Минус: дополнительные методы `schedule_reminders_for_task` / `remove_reminders_for_task`. Принято.

- **`send_reminder` race: lock → проверка → UPDATE флаг → commit → DM.** Внутри транзакции: `lock_for_update` → проверка `status IN (new, in_progress)` + `reminder_X_sent=False` → SET `reminder_X_sent=True` → commit. ПОСЛЕ commit'а — `send_dm_safe`. Если DM провалится — WARNING в лог, флаг уже стоит, повтор НЕ делаем. Почему: лучше потерять одно уведомление, чем держать row-lock на сетевой вызов к Telegram (могут быть секунды до flood/timeout). Альтернатива «откатывать UPDATE при ошибке DM» оставляет дыру для дублирующего уведомления при перезапуске бота. Принято осознанно.

- **`overdue_notif:<task_id>` Redis dedup, TTL=24h.** Spec из автономного промпта говорил «не уведомлять чаще раза в час». Заменено на 24ч после согласования с пользователем — иначе chronic-overdue задача спамит leads каждый час.

- **Получатели overdue DM**: leads ТОЛЬКО `task.department_id` отдела + ВСЕ admins. Не leads других отделов. Логика — overdue затрагивает ответственных за конкретный отдел; админы видят всё.

- **Purge только `status='done'` через 24ч от `completed_at`.** `cancelled` живёт в топике вечно — это исторический сигнал «эту задачу отменили, не делаем». По project_plan.

- **Bot-runtime accessor `app/bot/runtime.py`** — `set_bot()` / `get_bot()`, парный к `app/scheduler/runtime.py`. Job-функции APScheduler не получают bot через args (long-lived job'ы, передавать связку (bot, ...) через args тяжело при scheduler.add_job — args сериализуются в jobstore, и хотя у нас MemoryJobStore, всё равно громоздко). get_bot() — простой module-global. Инициализируется в main.py.

- **APScheduler EVENT_JOB_ERROR listener** добавлен в bootstrap — логирует exception на ERROR с job_id. Без него ошибки в job-функциях были бы глухими.

- **Redis-клиент для dedup переиспользует существующий клиент бота.** В main.py создаётся один `Redis()` инстанс для FSM storage; тот же клиент передаётся в notifications-модуль через global accessor `app/scheduler/notifications.py::set_redis(client)`. Не плодим лишних подключений.

- **Job ID-схема**: `reminder:{task_id}:{h2|d1|d2}` для напоминаний, `overdue_check` и `purge_completed` для interval'ов. Чистые ASCII, легко искать/удалять.

- **`misfire_grace_time=300s, coalesce=True`** — если бот лежал 5+ минут, job'ы за это время «коалесируют» в один прогон. Подходит для overdue_check / purge_completed (нет смысла стрелять 12 раз подряд) и для reminder'ов (один send_reminder для одного task'а — идемпотентен через флаг).

- **Зависимости НЕ менялись.** apscheduler 3.11.2 уже был в pyproject + uv.lock после Этапа 1.

## Пост-Этап 6: «Руководство» + защита polling + middleware-фикс

- **Доступ на запись в закрытую тему «Руководство» — штатным Telegram-механизмом, не своим whitelist'ом.** Сначала попробовали свою таблицу `leadership_whitelist` (миграция `c1d2e3f4a5b6`), через час дропнули (миграция `d2e3f4a5b6c7`). Источник правды — `closeForumTopic` + админ-право `can_manage_topics` в супергруппе. Бот ничего не хранит, ничем не управляет, только показывает текущий список через `/lead_list`. Почему: меньше кода, меньше синхронизации, меньше дыр; админ супергруппы — это уже доверенный человек по модели Telegram.

- **3-слойная защита polling от «тихой смерти».** Layer 1 — `_run_polling_supervised` в `main.py`: бесконечный try/except вокруг `dp.start_polling` с sleep 5s. Layer 2 — `_watchdog`: раз в 60s `bot.get_me()` с таймаутом 10s, на сбое cancel polling_task → supervisor рестарт. Layer 3 — Docker HEALTHCHECK читает `bot:heartbeat` из Redis (≤180s), `willfarrell/autoheal` следит за `autoheal: "true"` label на сервисе. Почему: `restart: unless-stopped` не помогает, когда процесс жив, а polling умер молча.

- **`bot.delete_webhook(drop_pending_updates=False)` перед `start_polling`.** Telegram держит «старую» getUpdates-сессию ~30-60 секунд после смерти прошлого процесса. При рестарте контейнера новый процесс ловит `TelegramConflictError`, пока серверный таймаут не освободит слот. `delete_webhook` сбрасывает это состояние мгновенно. `drop_pending_updates=False` — чтобы не терять обращения, накопившиеся за рестарт.

- **`AuthMiddleware` обёрнута в try/except.** До фикса любая ошибка БД в middleware пробивала наружу, aiogram молча скипал handler (логи только на DEBUG). Heartbeat-middleware стоит первой и успевала записать heartbeat — это вводило в заблуждение при диагностике. Фикс: ловим всё через `logger.exception`, ВСЕГДА вызываем `handler(event, data)` дальше. Если кто-то требует `data["user"]` — упадёт с понятным TypeError в `dp.errors()` handler'е.

- **`heartbeat.bump` обёрнут в `asyncio.wait_for(timeout=3)`.** Иначе залипший Redis вешает middleware-цепочку (heartbeat — первый middleware). 3 секунды — щедро для localhost Redis, но безопасно.

- **`dp.errors()` глобальный handler** добавлен в `main.py` — логирует исключения хэндлеров через `logger.exception`. Без него тихие падения handler'ов оставались только в DEBUG-логах aiogram.

- **`HEARTBEAT_KEY = "bot:heartbeat"`, TTL 600s, MAX_AGE 180s.** TTL >> MAX_AGE — чтобы healthcheck успел распознать stale-состояние раньше, чем сам ключ исчезнет (исчезновение ключа → healthcheck тоже fail, но через misleading «heartbeat missing» вместо «stale»).

- **Autoheal label-based фильтр (`AUTOHEAL_CONTAINER_LABEL: autoheal`).** Чтобы autoheal не перезапускал случайно постгрес/редис при их флапе healthcheck'а. Только сервисы с явным label `autoheal: "true"` — пока только bot.

- **Все файлы задачи шлются как `send_document`, не `send_photo` — по требованию пользователя.** Изначально была попытка диспатча по mime (фото → photo, документ → document), потом — попытка ZIP-архива; обе отброшены. Финальное решение: каждый файл отдельным сообщением, всегда `bot.send_document(...)`. Преимущество: единый UX (фото и документы выглядят одинаково — иконка «скачать», без inline-превью), сохраняется оригинальный формат, нет потерь при ресайзе/перекодировке (Telegram при `send_photo` мог бы пересжать). Минус: фото нельзя посмотреть прямо в топике, надо скачать — это ровно то, что заказчик и хотел.

- **Структурированное описание для отдела дизайнеров — 4 substate в FSM, без миграции БД.** Дизайнерам нужны типизированные поля (назначение, размеры, форматы, референс) для адекватной постановки. Реализовано через расширение `CreateTask` группы FSM (`design_purpose`, `design_sizes`, `design_formats`, `design_reference`) с ветвлением по `dept.code == "designers"` после шага deadline. Структура хранится как многострочный текст в существующей колонке `tasks.description` через `\n`-разделитель. Почему НЕ отдельные колонки в БД: (1) `tasks.description` уже TEXT и подходит, (2) для других отделов структура другая или её нет — таблица из 4 колонок только для дизайнеров была бы NULLable-мусором, (3) миграции — отдельное согласование, текстового хранения достаточно. Render распознаёт многострочное описание по наличию `\n` и выводит с переносами.

- **Универсальная навигация «⬅️ Назад» + «❌ Отменить» на всех шагах FSM создания задачи.** Все 11 точек prompt'а (включая ранее «голые» текстовые шаги title/deadline/design_*) получают inline-клавиатуру с минимум Cancel; промежуточные — ещё Back. Один callback `ct_back` обрабатывает возврат с любого шага через статический мап «текущий → предыдущий» (для `files`-шага ветвление по `department_code`). Перерисовка предыдущего prompt'а — через единый helper `_render_step_prompt`. Почему так: отсутствие кнопок на text-шагах ловило юзеров в тупик, если он случайно нажимал reply-кнопку главного меню во время FSM (текст «📁 Архив» уходил в title/deadline). Дополнительно — high-priority handler `msg_main_menu_during_fsm` перехватывает тексты главного меню во время FSM и предлагает явно отменить, а не парсит их как ответ на текущий шаг.

## Этап 7

- **Архив, контакты, статистика — три отдельных роутера** (`archive.py`, `contacts.py`, `analytics.py`). Все подключены ВЫШЕ `menu_stubs`, поскольку `menu_stubs` для оставшихся «🤖 Спросить AI» работает по `F.text.in_(...)` и не должен перехватывать наши кнопки.

- **Архив и статистика — через FSM (`ArchiveBrowse.viewing` / `AnalyticsBrowse.viewing`), а не FSM-less inline-state.** Состояние фильтров (отдел, исполнитель, статус, период, страница) хранится в `FSMContext.data`. Альтернатива «всё в `callback_data`» отброшена: 64-байтный лимит Telegram быстро упирается при 4-5 фильтрах. FSM в Redis уже есть как инфраструктура (используется для create_task), нет смысла плодить дополнительный слой.

- **Меню «👥 Контакты» — однократное сообщение без FSM.** Контакты — read-only, не имеют фильтров и пагинации (редакция = десятки сотрудников, не тысячи). Группировка по отделам делается рендером.

- **Архив фильтрует по `COALESCE(completed_at, created_at)` для сортировки и границ дат.** Для `status='cancelled'` `completed_at` может быть NULL (если отмена произошла из NEW и не выставила timestamp в коде task_actions, что валидно по спецификации). Фолбэк на `created_at` обеспечивает стабильный порядок и работу date-фильтра без NULL-провалов.

- **Employee видит только архив СВОЕГО отдела; фильтр отдела для него зафиксирован и в UI скрыт.** В `msg_archive_open` для employee автоматически выставляется `filter_dept = user.department_id`. Кнопка «🏢 Отдел: …» в фильтрах не появляется. Lead и admin видят все отделы. Это соответствует «обычный сотрудник видит свои задачи и задачи своего отдела» из PROJECT_PLAN.

- **Аналитика scope для lead = `department` по умолчанию, для admin = `all`. Дополнительно у обоих есть scope `user`.** Lead без `department_id` (граничный случай) автоматически попадает на scope `user`. У employee пункт «📊 Статистика» в главном меню вообще не отображается (см. `build_main_menu`).

- **Аналитика scope `user` — задача, где юзер либо creator, либо assignee** (`Task.creator_id == uid OR Task.assignee_id == uid`). Так покрывается полная картина «моих» задач без необходимости двух разных режимов «созданные» / «выполненные».

- **Период `week` и `month` — rolling 7d/30d, а не календарные неделя/месяц.** Rolling предсказуемее (не зависит от дня недели/месяца, в который зашёл), особенно для AI-агента (Этап 8): «за неделю» — это всегда последние 7 дней. `today` — от локальной полуночи (Europe/Moscow → UTC) до текущего now.

- **`overdue` в сводке — current snapshot, не за период.** То есть «сейчас просрочено», не «сколько ушло в просрочку за неделю». Это согласуется с реальным значением метрики для руководителя («что на грани, что горит прямо сейчас»).

- **`avg_completion_time` считается только для задач, завершённых в выбранный период.** Если ни одной — `None`, в UI «—». Это исключает скос из старых хвостов завершённых задач.

- **Карточка задачи в архиве рендерится одним сообщением: `render_task_card` + extra-блок (отдел, время закрытия) + `render_task_history`.** В одном сообщении удобнее, чем дробить на несколько. История — снизу как `<b>История:</b>` + локализованные строки событий из `task_history` (создана/принята/завершена/отменена/комментарий) с тай-брейкером по id.

- **Локализация payload событий: completed → `«result_comment»`, cancelled → `(by_role)`, commented → `(role): «text»`.** Все остальные ключи (если появятся при расширении) — игнорируются молча; рендер не падает.

- **Overdue-индикатор в `render_task_card`: статусная строка переключается на «🔴 Просрочена» при `status ∈ (new, in_progress) AND deadline < now`.** Заменяет «🆕 Новая» / «🟡 В работе» полностью. Для in_progress дополняется handle исполнителя. Реализация одна — на всё, что использует `render_task_card`: топик отдела, зеркало «Руководство», детальная карточка архива. Закрывает BACKLOG БЛОК-6.

- **Сортировка истории — `ORDER BY created_at ASC, id ASC`** (тай-брейкер по id, как требует BACKLOG). Закрывает соответствующий пункт BACKLOG.

## Пост-Этап 7: персональная продуктивность

- **`assigned` за период = `accepted_at` юзера в окне, не `created_at`.** Почему: при создании задачи assignee_id ещё NULL — ассайни появляется при «✋ Принять в работу». Логика «назначено мне за неделю» = «принято мной в работу за неделю».

- **«Создал» в карточке продуктивности НЕ показывается.** В task-bot задачи ставит только руководитель (см. memory `project_task_creation_role`). Для рядового сотрудника поле бессмысленно; для руководителя — отображается в общей статистике через scope=user, дублировать не нужно.

- **daily_breakdown группируется по локальной TZ (Europe/Moscow), не по UTC.** PostgreSQL: `date_trunc('day', accepted_at AT TIME ZONE 'Europe/Moscow')` — сначала конверт TIMESTAMPTZ → наивный локальный timestamp, потом trunc до дня. Иначе задачи, принятые в 22:00 MSK, попадут в день UTC раньше.

- **Плотный массив дней.** Daily-агрегаты двумя SQL-запросами (assigned, completed) → склейка в Python с заполнением нулями для всех дней периода. Это даёт ровный график без «провалов».

- **matplotlib Agg backend, DejaVu Sans.** Agg — серверный, без GUI. DejaVu Sans поставляется с matplotlib и содержит кириллицу, не нужен отдельный font-pack в Docker. `plt.rcParams["font.family"] = "DejaVu Sans"` зафиксирован, чтобы случайная замена дефолта не сломала рендер с кириллицей.

- **numpy<2.0 + matplotlib<3.10.** numpy 2.x требует x86-64-v2; сервер ivcurse — QEMU Virtual CPU с SSE2-only. numpy 1.26 — последняя версия 1.x, совместимая с CPU. matplotlib 3.10+ может тянуть numpy 2.x по lock-resolver'у, поэтому pin до 3.9. Зафиксировано в `pyproject.toml`, `uv.lock` перегенерирован.

- **Переход текст→фото — `delete()` + `answer_photo`, не `edit_text`.** Telegram API не позволяет конвертировать text-сообщение в media. При переключении периода (фото→фото) используется `edit_media(InputMediaPhoto)` с fallback на delete+send при ошибке.

- **Доступ: lead видит только свой отдел, admin — всех.** Проверка в callback handler-е через `_can_view_target(viewer, target)`. Прямой клик по callback'у `an:pu:<id>` чужого отдела для lead отдаст алерт. Это страховка от race / устаревших inline-клавиатур.

- **Период по умолчанию для карточки — `week`.** Совпадает с общей статистикой.

## Этап 8: AI-агент

- **Модель `gemini-2.5-flash`, не 2.0.** На текущем проекте Михаила квота 2.0-flash free-tier = 0; 2.5-flash работает. 2.5 умнее, function calling точнее. PROJECT_PLAN говорил «2.0 Flash» — отошёл от плана осознанно (см. ответ Google API).

- **SDK через native async (`client.aio.models.generate_content`).** Не `asyncio.to_thread` — google-genai 0.3+ имеет полноценный async-клиент.

- **AI = изолированный read-only слой.** Все tool-функции — обёртки над существующими репозиториями (READ-only). Единственная запись AI — `ai_conversations.messages`. Никаких изменений в `task_service` / `task_actions` / `scheduler` / FSM создания задач / БД-моделях. Это контракт: «AI как инструмент, не часть структуры проекта» (по требованию Михаила перед стартом Этапа 8).

- **Tool-loop ВНУТРИ одного ask(), в БД-историю только финальные text-turn'ы.** Альтернатива — сохранять весь tool-loop в `ai_conversations.messages` — даёт модели полный контекст прошлых разговоров, но раздувает JSONB и усложняет rehydration. На MVP выбран компромисс: история = чистые user/model текстовые сообщения, модель помнит «о чём говорила», но не помнит «что вернул инструмент».

- **8 инструментов (не 7 и не 9).** Из PROJECT_PLAN убран `suggest_task_formulation` (рекурсия Gemini-в-tool'е); добавлены `find_tasks` (поиск, не было в плане, но критично — нет другого UI) и `get_user_history` («что я делал на прошлой неделе»). Всё read-only.

- **Substring-поиск, не векторный.** `pgvector` в БД заложен, но эмбеддинги — отдельная инфраструктура (модель эмбеддингов + индексация при INSERT). На редакции с десятками задач substring через `ILIKE %query%` находит всё. Векторный поиск — BACKLOG.

- **System prompt в трёх блоках: BASE (статика, off-topic-отбивка) / DOMAIN_FACTS (статика, устройство проекта) / runtime (динамика, кто и когда спросил).** Off-topic ответ — ровно одна фраза «Я отвечаю только на вопросы про задачи редакции.» без извинений и альтернатив. Gemini 2.5 это правило соблюдает (проверено практически).

- **AI-ответы шлются с `parse_mode=None`.** Бот дефолтно использует `ParseMode.HTML`, но модель может вернуть `<`, `>`, `&`, которые сломают HTML-парс. Plain text безопаснее.

- **Лимит запроса юзера: 1000 символов.** Anti-dump в контекст. Telegram max 4096 — есть запас на ответ.

- **Тайм-аут Gemini 30s** через `asyncio.wait_for` → AiTimeout. Это меньше, чем серверный rate-limit окно (60s), и достаточно для одного-двух tool-call циклов.

- **Кеш Telegram-админов 5 мин (Redis SET).** Не AI, но для team.py — добавлено вместе с AI, чтобы `_is_chat_admin()` не делал get_chat_administrators на каждый клик. (Закрепил здесь, потому что использует `app/bot/utils/access.py`.)

- **Permission-логика внутри tools, не на уровне роутера.** Каждая функция сама понимает «текущий юзер employee → подменю user_id на ctx.user_id». Так агент может вызывать tool с произвольными args от модели — функция вернёт корректные данные либо `{"error": ...}`, и модель адаптируется.

- **`AiConversationsRepository.extend` для пачки сообщений за раз.** Чтобы за один `await session.flush()` записать user_msg + model_msg, не плодить транзакции.

## Этап 9: коробочное решение

- **`scripts/` директория с bash-скриптами, не Python.** Все деплой-операции (preflight, backup, restore) должны работать ДО того, как `pip install` / `uv sync` будут выполнены. Bash + базовые утилиты есть на любом Linux-сервере, Python-зависимости — нет.

- **Бэкапы в `./backups/` (хост FS), не в Docker volume.** Чтобы клиент мог `scp -r backups/` забрать архив, а также чтобы dump-файлы переживали `docker compose down -v`.

- **Ротация бэкапов через shell-find без `logrotate`/`restic`.** Простота важнее: клиент видит скрипт целиком, понимает что происходит. 14 ежедневных + 4 воскресных — оптимально для редакции, где данные не критичны для бизнеса (потеря дня — неприятно, но не катастрофа).

- **AI rate-limit per-user через Redis `INCR + EXPIRE NX`, TTL до полуночи MSK.** Атомарно (не race), TTL не сбрасывается при повторных запросах (NX-флаг). `AI_USER_DAILY_LIMIT=0` отключает лимит — для разработки/тестов.

- **`AI_USER_DAILY_LIMIT=30` дефолт.** На редакцию 5-10 человек квота Gemini 250/сутки делится с запасом: 30 × 5 = 150, остаётся 100 на пиковые дни. Если клиент захочет — выкручивает в .env.

- **Sentry НЕ включён по умолчанию.** Loguru пишет в stdout, `docker compose logs` сохраняет последние N МБ (по дефолту 200 МБ rolling). Для редакции из 5 человек этого достаточно. Если клиенту нужен централизованный мониторинг — отдельная фича.

- **`Makefile` как точка входа для всех операций.** Клиент учит ОДИН синтаксис `make <command>`, не запоминая длинные `docker compose ...` команды.

- **`preflight.sh` exit code 1 при ошибках.** Чтобы можно было использовать в pre-deploy hook'ах CI/CD.

## Личный кабинет (post-Этап 9)

- **Кабинет — отдельная кнопка `👤 Кабинет` в главном меню, доступна ВСЕМ ролям.** Раньше любая статистика была только у lead/admin (employee «слепой»). Кабинет — это scope=user без переключателя scope: только собственные числа и задачи. У lead/admin рядом остаётся `📊 Статистика` для обзора отдела/всех. Не объединял в одну кнопку, чтобы у lead/admin осталась ясная пара «моё (кабинет)» vs «команда (статистика)».

- **Время реакции (`created → accepted`) НЕ показывается в кабинете.** В task-bot задача создаётся без исполнителя и висит свободной в общем топике, пока кто-то из отдела её не возьмёт. Это интервал зависит не от конкретного сотрудника, а от того, кто первый увидел и нажал «Принять». Считать это «реакцией конкретного исполнителя» — несправедливо. Оставлено только «среднее время выполнения» (`accepted → completed`).

- **Активные задачи разложены лесенкой по «температуре дедлайна», категории взаимоисключающие.** Порядок проверки: `overdue` → `burning_24h` (0..24ч) → `today` (редкий остаток после 24ч в рамках того же локального дня) → `this_week` (1..7д) → `later` (≥7д). Каждая задача попадает ровно в одну корзину. Альтернатива «горит И сегодня одновременно» отброшена: пересекающиеся группы путают глаз.

- **`cancelled` для кабинета берётся из `task_history` (event=cancelled в окне), а не из `tasks.status='cancelled' + completed_at`.** При действии `cancel` поле `completed_at` не выставляется (см. `services/task_actions.py:cancel`). Считать отменённые через статус+completed_at — невозможно. История — единственный надёжный источник «когда отменили».

- **«Залипшие» — `in_progress` + последнее событие в `task_history` > 7 дней назад.** Через коррелированный `MAX(created_at)` подзапрос по `task_history` каждой задачи, с fallback на `accepted_at` если истории нет вообще. На объёмах редакции (десятки активных задач) производительность ок. При росте — переписать через window function.

- **Свободные задачи (`status='new' AND assignee_id IS NULL`) показываются ПО ВСЕМ ОТДЕЛАМ.** Топики в task-bot открыты всем (см. memory `topics_open_access`), отдел — это тег задачи, а не группа доступа. Поэтому фильтровать по отделу юзера было бы искусственным ограничением. Имя отдела включается в подпись каждой строки.

- **Deeplink на сообщение задачи: `https://t.me/c/<chat_id_normalized>/<topic_id>/<message_id>`.** Нормализация: `abs(chat_id) - 1_000_000_000_000`. Номер `#ID` оборачивается в `<a href="…">` если есть `dept_chat_id`+`dept_message_id`+`department.topic_id`. Если у задачи нет message_id (outbox ещё не доставил) — показывается просто `#ID` без ссылки, без падений.

- **Кнопка `🔄 Обновить` ловит `message not modified` как норму.** В кабинете данные часто не меняются между кликами — Telegram возвращает edit-ошибку, мы её логируем на DEBUG и показываем `cq.answer("Обновлено")` без alert. Без этого юзер видел бы красный alert при безобидном обновлении.
