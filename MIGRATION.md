# Миграция на новый сервер с сохранением всех данных

Эта инструкция — для случая, когда бот переезжает на новую инфраструктуру
**с переносом всей накопленной базы**: задачи, история статусов и комментариев,
пользователи и их роли, отделы, метаданные вложений, вся переписка с
AI-ассистентом (`ai_conversations`), настройки (`app_settings`).

Общая установка (сервер, Docker, супергруппа, топики) описана в
[README.md](README.md) — этот файл описывает **только отличия**, когда
разворачиваетесь не с нуля, а поверх готового дампа БД.

## Что входит в дамп

Файл `taskbot-YYYY-MM-DD-HHMM.sql.gz` — это `pg_dump --clean --if-exists`
всей базы `taskbot`. При восстановлении он **полностью замещает** содержимое
целевой БД (дропает и пересоздаёт таблицы), поэтому его безопасно накатывать
как на пустую, так и на уже засеянную дефолтными данными базу.

Внутри:

- `tasks`, `task_history`, `task_files`, `task_broadcasts`, `task_outbox` — все задачи и их история целиком
- `users` — все сотрудники: `tg_user_id`, имя, роль, отдел, `access_status`, `is_active`
- `departments` — отделы вместе с их `topic_id` (привязка к топикам старой супергруппы)
- `ai_conversations` — история переписки пользователей с AI-ассистентом
- `app_settings` — включая `TASK_CHAT_ID`, `LEADERSHIP_TOPIC_ID`, `onboarding_approver_tg_id`

**Важно про `departments.topic_id` и `app_settings.TASK_CHAT_ID`.** Это внутренние
Telegram-идентификаторы **той самой старой супергруппы и её топиков**. Они
привязаны к чату, а не к боту — значит:

- Если задачи и переписка продолжатся **в той же самой существующей супергруппе**
  (просто новый бот добавляется в неё вместо старого) — эти значения после
  restore уже правильные, `/set_chat` и `/set_topic` **повторно делать не надо**.
- Если разворачиваете **новую супергруппу** — старые значения будут указывать
  в никуда. В этом случае после restore обязательно перепройти Шаг 5 из
  README (`/set_chat`, `/set_topic` на каждый топик, `/set_leadership_topic`)
  для новой группы. Старые задачи при этом останутся в БД и будут видны в
  архиве/статистике, но их карточки в старых топиках (если старая группа вообще
  сохранится) новым ботом уже не редактируются — Telegram не даёт одному боту
  править сообщения, отправленные другим ботом.

## Пошагово

### 1. Обычная установка до состояния «бот отвечает на /start»

Пройти **Шаг 1–4 README.md** полностью: свой `BOT_TOKEN` через `@BotFather`,
свой `ADMIN_TG_ID` (свой личный Telegram-id — это станет резервным входом
админа даже поверх восстановленных данных, см. пункт 4 ниже), при желании
`GEMINI_API_KEY`, `.env`, `make preflight`, `make up`.

Дождитесь, что `make logs` показывает «Запуск polling» — то есть новый бот
уже работает, но пока с **пустой/дефолтной** базой (3 отдела без `topic_id`,
один админ = ваш `ADMIN_TG_ID`). Это нормально, дальше она будет замещена.

### 2. Скопировать дамп на новый сервер

Дамп лежит вне git-репозитория (`backups/` в `.gitignore` — в нём реальные
данные сотрудников, поэтому передаётся отдельно, не через GitHub). Скопировать
файл `taskbot-YYYY-MM-DD-HHMM.sql.gz`, например через `scp`, в
`/opt/task-bot/backups/` на новом сервере.

### 3. Восстановить дамп

```bash
make restore F=./backups/taskbot-2026-09-14-0958.sql.gz
```

Скрипт даёт 5 секунд на отмену (Ctrl+C), затем полностью замещает БД
содержимым дампа. После восстановления — обязательный рестарт бота, чтобы
сбросить любое закэшированное в процессе/Redis состояние:

```bash
docker compose restart bot
```

### 4. Добавить себя админом поверх восстановленных данных

Восстановленная база несёт **старый** список пользователей — вашего
`ADMIN_TG_ID` там, скорее всего, нет (если только это не тот же человек,
что был админом в старой системе). Сидер идемпотентен: повторный запуск не
трогает уже существующие записи, только добавляет отсутствующие. Выполните:

```bash
docker compose exec bot python -m app.db.seeders
```

Он допишет вашего `ADMIN_TG_ID` как ещё одного админа, не изменив ни одного
существующего пользователя, отдел или задачу. После этого зайдите в личку
бота и отправьте `/start` — должны сразу увидеть главное меню админа, без
экрана «ожидайте одобрения».

Если ваш собственный `tg_id` **уже был** в старой системе (например, вы уже
были admin/lead там) — реcтор его роль восстановит автоматически, шаг с
seeders можно пропустить, `/start` сразу пустит по старым правам.

### 5. Проверить целостность

```bash
make shell-db
taskbot=# SELECT count(*) FROM tasks;
taskbot=# SELECT id, code, name, topic_id FROM departments;
taskbot=# SELECT tg_user_id, full_name, role, is_active FROM users;
taskbot=# SELECT * FROM app_settings;
```

Числа задач и список пользователей должны совпадать с тем, что было в старой
системе.

### 6. Привязка к супергруппе (только если группа новая — см. предупреждение выше)

Повторить Шаг 5 из README: `/set_chat` в общем чате, `/set_topic` в каждом
топике отдела, `/set_leadership_topic` в топике «Руководство».

Если группа осталась той же самой — этот шаг пропускается, значения уже
верны из дампа.

## Частые проблемы при миграции

**После restore бот не видит старые задачи в топиках, хотя в БД они есть**

Ожидаемо, если группа новая — карточки физически существовали только в
старой группе/у старого бота. Данные в БД целы (видны в архиве, статистике,
через AI-ассистента), просто визуальные карточки в топиках новой группы для
старых задач не появятся сами — это не баг, это следствие того, что каждая
карточка это конкретное Telegram-сообщение конкретного бота в конкретном чате.

**`docker compose exec bot python -m app.db.seeders` падает с ошибкой подключения к БД**

Значит restore ещё не закончился или контейнер `bot` не успел переподняться
после `docker compose restart bot`. Проверить `docker compose ps` — все три
контейнера должны быть `healthy`/`running` перед этим шагом.

**Нужно откатиться, если restore пошёл не так**

Восстановление необратимо перезаписывает БД в моменте выполнения. Если до
восстановления вы уже успели поработать в новой (пустой) базе и не хотите
это терять — сделайте `make backup` **перед** `make restore`, чтобы иметь
дамп текущего состояния для отдельного отката.
